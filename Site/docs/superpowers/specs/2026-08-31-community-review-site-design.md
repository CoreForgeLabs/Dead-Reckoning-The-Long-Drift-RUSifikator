# Публичный сайт вычитки перевода Dead Reckoning

Дата: 2026-08-31

## Задача

Довести `zen_server.py` до состояния, в котором его не стыдно открыть
посторонним: смотреть текущий перевод, голосовать за строки, предлагать свой
вариант, видеть предложения других. Источник истины — репозиторий
`CoreForgeLabs/Dead-Reckoning-The-Long-Drift-RUSifikator`. Хостинг сейчас — тот
же компьютер, порт наружу не выведен; перенос на отдельный VPS — следующий шаг
после того, как сайт стабилен, и в объём этой спеки не входит.

## Что сейчас сломано

Прочитал `zen_server.py` целиком, а не поверил README. Три находки решают
форму дизайна:

1. **Права проверяются на слове клиента.** `/api/review` берёт
   `is_admin` из тела POST-запроса — `req.get("is_admin", False)`. Открыть
   консоль браузера и отправить `{"is_admin": true}` может кто угодно, и
   правка тут же получает статус «одобрено администратором».
   `/api/accept_suggestion` ещё хуже: там нет даже такой видимости проверки —
   маршрут безусловно пишет `status: "admin_approved"` и тут же перезаписывает
   `locales/ru/*.json` на диске.
2. **Личность — голая IP-строка.** `/api/vote`, `/api/vote_suggestion`,
   история правок — everywhere ключ идентичности это `client_ip`. Общий
   NAT/офисная сеть/мобильный оператор — и десять разных людей голосуют как
   один; сменился IP — человек теряет свой голос и может проголосовать снова.
3. **Путь синхронизации мёртв.** `prepare_data.py` берёт исходник из
   `F:\...\Dead Reckoning Russifier\dist_tools\dist\data` — эта папка снесена
   при уборке проекта-переводчика 30 августа. Плюс скрипт работает с
   `remap.json`, которого в поставке больше нет — актуальное имя
   `remap_by_en.json`. У `repos/dead-reckoning` нет `git remote` вообще: это
   была разовая ручная копия, не живая связь с GitHub.

Существующая модель функций (посмотреть, что уже есть, чтобы не
переизобретать) в целом правильная и остаётся: голос за/против текущего
перевода строки, предложение своего варианта, голос за предложение, принятие
предложения. Меняется не набор действий, а то, кому они верят и куда пишут.

## Архитектура

Один Python-процесс, как сейчас (`http.server`, без фреймворка) — менять не
за чем, нагрузка небольшая. Хранилище состояния — **SQLite** вместо
`data/zen_state.json`: тот же инструмент, что уже отработал на конкурентном
доступе в пайплайне перевода, и он снимает главную проблему JSON-файла —
запись из нескольких запросов подряд без блокировок.

```
zen_server.py           -- как сейчас, HTTP-хендлеры переписаны на SQLite
zen_review.db           -- новое хранилище: identities, votes, suggestions,
                            suggestion_votes, history
data/source_baseline/   -- то, что реально сейчас лежит в main репозитория
                            (свежий git pull), НЕ то, что можно менять сайтом
```

### Личность

При первом визите без cookie сервер создаёт запись `identities` (случайный
токен, IP создания, время) и ставит cookie на год. Ник — опциональное поле
поверх токена, меняется в любой момент, к нему привязки правок нет — вся
принадлежность идёт по токену. Если пользователь ничего не выбрал, действия
подписаны «Аноним».

Регистрация нового токена ограничена: сервер считает, сколько токенов уже
выпущено с этого IP за всё время, и после первого отказывает (`429`, понятное
сообщение). После выпуска токен работает с любого IP — привязки к IP после
создания нет.

```sql
CREATE TABLE identities (
    token       TEXT PRIMARY KEY,
    nickname    TEXT,
    created_ip  TEXT NOT NULL,
    created_at  TEXT NOT NULL
);
CREATE INDEX idx_identities_ip ON identities(created_ip);
```

### Права администратора

Список админ-токенов — фиксированный набор в переменной окружения
(`ZEN_ADMIN_TOKENS`, через запятую), читается один раз при старте процесса.
Ни один маршрут никогда не принимает `is_admin` от клиента: сервер сам
смотрит, есть ли cookie-токен запроса в этом списке, и это единственный
источник административных прав.

### Данные: голоса, предложения, история

```sql
CREATE TABLE votes (
    uid     TEXT NOT NULL,          -- "<component>::<key>"
    token   TEXT NOT NULL,
    value   INTEGER NOT NULL,       -- 1 или -1
    ts      TEXT NOT NULL,
    PRIMARY KEY (uid, token)
);

CREATE TABLE suggestions (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    uid         TEXT NOT NULL,
    text        TEXT NOT NULL,
    comment     TEXT,
    author      TEXT NOT NULL,      -- token
    created_at  TEXT NOT NULL,
    status      TEXT NOT NULL DEFAULT 'open'
                -- open | community_approved | admin_approved | rejected
);

CREATE TABLE suggestion_votes (
    suggestion_id  INTEGER NOT NULL REFERENCES suggestions(id),
    token          TEXT NOT NULL,
    value          INTEGER NOT NULL,
    PRIMARY KEY (suggestion_id, token)
);

CREATE TABLE history (
    uid       TEXT NOT NULL,
    old_text  TEXT,
    new_text  TEXT NOT NULL,
    actor     TEXT NOT NULL,        -- token
    action    TEXT NOT NULL,        -- suggested | community_approved | admin_approved
    ts        TEXT NOT NULL
);
```

**Порог принятия.** Предложение переходит `open -> community_approved`
автоматически, когда его чистый счёт (`up - down` по `suggestion_votes`)
достигает `+3`. Админ может выставить `admin_approved` или `rejected` в любой
момент вручную, независимо от счёта голосов, — это единственный способ попасть
в `admin_approved`, автоматики для него нет. Оба статуса, `community_approved`
и `admin_approved`, попадают в экспорт; `rejected` и `open` — нет.

**Ключевое изменение поведения:** ни голос, ни принятие предложения **не
трогают файлы на диске**. `data/source_baseline/*.json` — это снимок `main`,
он read-only для сайта, обновляется только через `git pull`. «Принятая»
строка — это запись в `suggestions.status`, а не запись в JSON. Сайт держит
две вещи рядом для каждой строки: официальный текст (из `main`) и текущее
состояние предложений/голосов по ней. Старое поведение (правка сразу
становится тем, что видят все посетители, без просмотра) уходит: теперь это
видно как отдельный слой поверх официального текста, явно помеченный.

Причина: сайт — витрина сообщества, а не параллельный источник истины. Два
живых источника «текущего перевода» уже один раз стоили проекту выкатки
позавчерашнего текста разработчику — воспроизводить эту ошибку здесь не
нужно.

### Синхронизация с GitHub

**Чтение.** Кнопка «Обновить перевод» в админ-панели делает `git pull` в
`repos/dead-reckoning` (ветка `main` того же `CoreForgeLabs/...RUSifikator`),
затем копирует `rusifikator/data/*.json` в `data/source_baseline/`. Это то,
что реально видит игрок в игре — источник для колонки «официальный перевод»
на сайте. Автоматика по расписанию (крон) не входит в этот проход — не
просили, действие редкое (несколько раз в неделю по факту наших пушей), ручной
кнопки достаточно.

**Запись.** Отдельное действие «Выгрузить предложения сообщества»
(кнопка в админ-панели, не автоматика): берёт все `suggestions` со статусом
`community_approved` или `admin_approved`, собирает патч в формате поставки
(`{key: text}` по каждому файлу), коммитит в ветку `community-suggestions`
того же репозитория и делает `git push`. `main` сайт никогда не трогает —
слияние `community-suggestions` в `main` смотрится и делается вручную, через
пайплайн проекта-переводчика (лингвистическая проверка, не автослияние).

Обе стороны идут через один и тот же локальный клон `repos/dead-reckoning` с
уже настроенным `git remote` (сейчас remote отсутствует — это первое, что
чинится в реализации).

## Что уходит из этого прохода

- Docker / `docker-compose.yml` / полноценный Weblate — решили не доводить.
  Файлы можно оставить в репозитории как задокументированную альтернативу,
  но `README.md` перестаёт представлять Weblate как рабочий путь.
- Скрипты `import_to_weblate.py`, `setup_components.py`,
  `setup_all_components.py`, `reload_weblate.py`, `export_weblate_to_dist.py`
  — специфичны для Weblate-пути, использования не найдут. Не удаляю в этой
  спеке (решение об удалении — на реализации, после явной проверки, что
  ничего от них не зависит).
- Развёртывание на VPS — отдельная задача после того, как локальная версия
  стабильна.
- Обсуждения/комментарии сверх поля `comment` у предложения — не просили,
  не добавляю.

## Миграция существующих данных

`data/zen_state.json` уже содержит одну реальную запись (ревью строки
`extra::earth literature`). При первом запуске новой версии сервера — разовый
скрипт переноса: читает JSON, создаёт по нему записи в `identities` (IP из
старых записей становится `created_ip` синтетического токена),
`votes`/`suggestions`/`history` по той же схеме. После успешного переноса
`zen_state.json` переименовывается в `zen_state.json.migrated`, не удаляется.
